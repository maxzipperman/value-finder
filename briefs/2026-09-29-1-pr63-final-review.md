## The rule the code must implement, exactly (the hub's decisions)
## THE ACCOUNTING RULE (the hub's decision; implement exactly this, for the bulk puller and so for odds-pull)

What a run COUNTS toward --max-credits:
1. An answered call counts the larger of its reported cost (x-requests-last, rounded up) and its documented cost (worked out from the call and the body, as the branch already does).
   - If the reported cost cannot be read on a billed (HTTP 200) answer: count the call's upper bound and stop; the billing could not be read.
   - If the reported cost is below the documented cost on an answer that carries data: count the documented cost and stop; the billing cannot be trusted.
   - If the reported cost is above the call's upper bound: count it and stop; the call was charged more than it can cost.
2. Every attempt that got no answer (a timeout, a dropped connection) counts the call's upper bound, and stays counted to the end of the run. It is never cleared.
3. THE BALANCE NEVER ADDS TO THE COUNT. Remove the counting of falls in the balance, the clearing of unanswered attempts, the three-in-a-row breaker and the adjustments for a rising balance.
3a. EVERY HTTP RESPONSE IS AN ANSWER, including one that is about to be retried (an HTTP 429 or 5xx). Its billing headers are read BEFORE the decision to retry: a readable reported cost is counted; with no readable cost the call's upper bound is counted, as for an attempt with no answer; its balance is read like any other; and if it reports a cost above the call's upper bound the run stops there and does not retry (audit finding C2: a 500 that reported 300 credits was followed by a retry that bought 30 more).
3b. After the last answer of a call, if the count has passed --max-credits the run stops with a STOPPED line; a call never returns as done while the run is over its budget.
Before every attempt, first try or retry: if the count plus the call's upper bound would pass --max-credits, stop on the budget.

What a run does with the BALANCE (x-requests-remaining):
4. The key check at the start must return a readable balance at or above the floor, as now. Call it the start.
5. After each answered call with a readable balance, remember the lowest balance reported so far.
6. A reading HIGHER than the one before it. If it is higher by MORE than the margin (rule 8), credits were added or the month renewed: log a WARNING each time this happens, and start again from there (the start becomes that balance plus the count so far, and the lowest becomes that balance). If it is higher by the margin or less, it is an out-of-date reading: ignore it (the start and the lowest do not change), count it in a tally, and log that tally once when the pull ends. (The last review showed that treating every small rise as credits added lets a header whose lateness varies switch the alarm off.)
7. The floor. The run's estimate of the balance is the smaller of (the lowest balance reported) and (the start minus the count so far). Before every attempt: if that estimate minus the call's upper bound is below --floor, stop on the floor.
8. The one alarm. The unexplained fall is (the start minus the lowest balance reported) minus (the count so far). If it is ever more than the margin, stop with a line that says the account has fallen by that many credits more than this run counted; that the cause is one of three things (something else is spending on this key, the balance header runs behind the charges, or the API is charging more than it reports); and to run 'markets odds5m headers' and tell the hub before rerunning. THE MARGIN is the larger of 5,000 credits and 10% of --max-credits, unless the operator sets it with a new option, --alarm-margin N (N at least 300), on the probe, week and full stages and on odds-pull. Every run prints the margin in force on its first line after the key check.
9. A billed answer with no readable balance while a floor is set stops the run, as now.

Why this is safe to reason about: a balance header that is late, by any number of answers and by a varying number, can only make the lowest balance HIGHER than the truth, so it can only delay the floor stop and the alarm by that many answers; it can never stop an honest run. Attempts with no answer make the count higher, so they too can never raise the alarm. What can still be lost beyond --max-credits is bounded and must be stated in the runbook in one short paragraph: one call charged above its upper bound (the run stops right after it); and, if the API charges more than it reports, the margin plus the charges of as many answers as the balance header is late. At 5,000,000 credits for $119, a margin of 8,500 credits on the largest day-one pull is about 20 cents.

## WHY THE ALARM IS NOT TIGHTER (the hub's reasoning; put it in the runbook in plain words, shorter)
Nobody knows yet how the real API's balance header behaves: live, a few answers late, or refreshed in steps. A header that runs late makes an honest run look as if the account fell by more than the run counted, for as many credits as the header is late. The alarm cannot tell that apart from overcharging, so its margin has to be wider than the header's lateness, and the lateness has to be MEASURED on the first real calls, which cost one credit each (the probe's schedule sweeps), before any large pull. That is what the new 'headers' stage is for. The hub runs Thursday's commands by hand and reads each result, so a stop that turns out to be a late header costs a minute; an overcharge that goes unseen costs credits. When in doubt the code stops.

## What counts as realistic (the hub's definition; judge severity by it)
THE REALISTIC API: every answer reports its true cost; every charge is within its upper bound; the balance header is live, or late by up to 100 answers (a fixed or a varying number), or refreshed in steps of up to 100 answers; other users of the key spend up to 500 credits during a run; up to 5% of attempts time out.
Behaviour outside that (an API that charges more than it reports, a header that never moves, a header later than 100 answers, a garbled header) is a FAULT CASE. In fault cases the code must fail toward stopping, and the loss must be bounded as the runbook states; a fault case that stops an honest-looking run is NOT a blocker, and must be cheap to clear with the 'headers' stage and --alarm-margin.

Severity: blocker = against the realistic API, with the default margin, a day-one command as printed in the runbook is stopped by the alarm, or a run passes its budget or floor by more than one call's upper bound; in a fault case, credits are lost beyond what the runbook states; a key can reach text or a file; a sealed row can be read; a runbook command fails on the happy path; the 'headers' stage makes any network request. major = a rule not implemented as written; old balance accounting left in; the 'headers' verdict or advised margin wrong on any of its test manifests; a runbook sentence that does not match the code; a change to what is bought other than the NHL's three sweeps and H1's 27 calls. minor = the rest.
